# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Sheet Music Tuner: a violin-first practice app. The user uploads sheet music, the app identifies the notes, and while the user plays through the piece the app listens and tracks intonation against the *expected* note (score-following) rather than acting as a generic tuner. Full product rationale and phased feature roadmap live in `sheet-music-tuner-plan.md` (condensed to a short working-contract pointer at `.github/copilot-instructions.md` for Copilot — not a full mirror). Key rules from that contract that still apply:

- Do not build out Phase 1 score/UI features in a way that regresses the Phase 0 pitch-detection gate — changes to the pipeline should stay measurable via `npm run phase0:validate`.
- Violin-only frequency focus: ~80Hz–3.5kHz. Prefer emitting "no note" over guessing on silence/low-confidence frames — correctness and stability over aggressive detection.
- Both the MusicXML import path and the OMR (photo) import path must normalize into the single shared `ScoreDocument` schema in `score/schema.ts`.

This repo is a **Vite/React web prototype**; the long-term target platform per the plan doc is React Native + Expo with native iOS (Swift/AVAudioEngine) and Android (Kotlin/AudioRecord) capture. `audio/captureModule/ios` and `audio/captureModule/android` are unwired native-bridge stubs for that future migration.

## Commands

Node/TypeScript side (repo root):
```bash
npm install               # Node 20+
npm run typecheck         # tsc --noEmit, covers audio/ score/ practice/ storage/ src/
npm run build              # tsc build
npm run dev:web            # Vite dev server at https://localhost:5173 (self-signed cert; HTTPS is forced because mic capture needs it)
npm run build:web          # production web build
npm run preview:web        # preview the production build
```

There is no unit test framework (no Jest/Vitest). Correctness for the pitch-detection pipeline is instead checked by an offline validation harness against recorded/synthetic `.wav` fixtures:
```bash
npm run phase0:generate-synthetic   # regenerate synthetic test tones into audio/__tests__/offline-validation/dataset
npm run phase0:validate             # run the acceptance gate (see audio/__tests__/offline-validation/README.md)
```
The gate checks: >=95% steady-state frame accuracy, <=1 octave error across the dataset, no spurious pitch on rest windows, and <=150ms mean onset latency. `ground-truth.json` and the `dataset/` directory are gitignored — copy `ground-truth.example.json` to `ground-truth.json` and add your own `.wav` clips locally.

`practice/cursor.ts`'s `ScoreFollower` (score-following/tracking) has its own offline harness, same rationale, different scope — synthetic frame sequences against a mocked `ScoreCursor` rather than recorded audio:
```bash
npm run followerTest                # runs practice/__tests__/resync-harness.ts
```
This only exercises tracking *decision logic*; see the score-following section below for what it structurally can't catch (anything touching the real OSMD cursor object, or real signal noise) and why a green run here isn't sufficient on its own.

Python side (`server/`) — a separate FastAPI microservice, not part of the Node toolchain:
```bash
cd server
pip install -r requirements.txt
uvicorn main:app --reload --port 8000
```
It requires `uv`/`uvx` on PATH (used to invoke the `homr` optical-music-recognition CLI on demand — `uvx homr <image>` fetches and runs it without a separate install step). If `uv` was installed after the terminal running `uvicorn` was opened, that process still has the old PATH — restart the terminal (or the whole IDE, if it's an integrated terminal) before re-testing.

Both the Vite dev server and this Python server must be running simultaneously for the sheet-music-photo-import feature to work end-to-end.

## Architecture

### Two independent runtimes
- The **web app** (`src/`, `audio/`, `score/`, `practice/`, `storage/`) is TypeScript/React, built with Vite.
- The **OMR microservice** (`server/main.py`) is a standalone Python FastAPI process. It has no code sharing with the TS side — the contract between them is purely the HTTP JSON shape of `POST /api/parse-sheet` (see below). Its CORS allowlist must match the Vite dev server's actual origin/scheme (`server/main.py`'s `allow_origins` vs. `vite.config.ts`'s forced `https://localhost:5173` — these have drifted out of sync before; check both when touching either). `_extract_notes_from_musicxml` filters to a single `<voice>`, mirroring `score/musicxmlImport.ts`'s voice-filtering — keep these two in sync if that convention changes, same as the pitch-string-format rule below. homr's subprocess timeout is configurable via the `HOMR_TIMEOUT_SECONDS` env var (default 60s); failures are logged server-side (stdout/stderr, tracebacks) but not echoed to the client response.

### Live tuner pipeline (`audio/`)
`audio/captureModule/index.ts` (`BrowserMicrophoneCaptureController`) is the only runtime consumer of the pitch detector, and the only thing `src/App.tsx` talks to for live tuning. Flow: `getUserMedia` → `AudioWorkletNode` → a ~500ms auto-calibration phase (aggregates ambient noise RMS via median, not mean, so one transient loud sample can't skew the threshold, to set `silenceRmsThreshold` and a gain scalar) → framing (`frameSize`/`hopSize`) → `preprocessFrame` (`audio/preprocessing.ts`: biquad band-pass *then* noise gate — filtering first so out-of-band noise can't inflate the gate's RMS reading — then a Hann window) → `PitchDetector.detect()` (`audio/pitchDetector.ts`). A liveness watchdog restarts the whole pipeline if the worklet stops posting messages entirely for ~4s while listening/calibrating (reset on every message received, regardless of loudness) — deliberately decoupled from signal RMS, since gating it on "quiet" used to fire on ordinary silent practice pauses while missing the actual stuck-worklet case it's meant to catch.

`PitchDetector` is a hybrid, not a single algorithm: primary estimate from `pitchfinder`'s YIN, a hand-rolled normalized-autocorrelation search as fallback (or as the primary path when an `expectedFrequencyHz` hint narrows the search window — this hint mechanism is not currently wired to score-following; see the score-following section below for why turning it on isn't a free accuracy win), a difference-function heuristic to catch octave-halving errors (gated on a 150–1500Hz frequency band and a 0.2–0.55 confidence band — narrow bands specifically because a *confident* reading almost never needs octave correction, and this heuristic works from signal shape alone with no awareness of the score's expected pitch), and a rolling median smoother (`smoothingWindowFrames`, default 5). Confidence is computed separately via normalized cross-correlation at the detected lag. `src/App.tsx`'s `LIVE_CAPTURE_OPTIONS.confidenceThreshold` (`0.67`) gates this at the call site — below it, `detect()` returns `frequencyHz: null`, which the UI already renders as "No note" (`noteDisplay` in `App.tsx`). This was previously `0.4`, permissive enough that background noise routinely registered as a confidently-detected pitch — don't lower it back without a specific reason.

`PitchDetectionResult.reason` (`"silence" | "low_confidence" | "outside_expected_window" | "detector_no_pitch" | "outside_violin_range"`) is set on every rejection path but was computed and then silently discarded before reaching any consumer — `LivePitchFrame.reason` (and `LiveCaptureState.reason`) now mirror it through `captureModule/index.ts`'s `toLiveFrame()` (null instead of undefined on a confident reading). Purely additive/diagnostic — no decision logic reads it directly in the audio layer, it exists so a consumer (see `ScoreFollowerState.lastPitchReason` below) can distinguish *why* a frame produced no usable pitch instead of collapsing every rejection into the same null.

`audio/onsetDetector.ts` (`OnsetDetector`, spectral-flux based) is wired into `audio/captureModule/index.ts`, which emits `onsetDetected` on every live frame. It has a fundamental blind spot: no attack transient to catch on a legato/slurred bow change, so `practice/cursor.ts`'s `ScoreFollower` has a second, independent note-change trigger to compensate — see the score-following section below.

**Frame-buffer timing bug (fixed, but worth knowing the shape of)**: `processBufferedFrames()`'s overlapping-frame consumption (`hopSize` 512, `analysisFrameSize` 2048/4096 depending on device sample rate) used to special-case "buffer length exactly equals frameSize" by resetting the buffer to 0 instead of the correct shift-by-`hopSize` — and because audio arrives in small fixed-size chunks (128-sample Web Audio render quantums) that evenly divide both `hopSize` and `frameSize`, that was the path taken on nearly *every* iteration, not a rare edge case. This silently discarded the `frameSize - hopSize` samples that should have carried over for the next overlapping window, meaning a *full* `frameSize` of new real audio had to arrive before the next analysis frame could run at all, while `nextFrameStartSampleIndex` (and therefore every `LivePitchFrame.timestampMs`) still only advanced by `hopSize` each time — undercounting real elapsed time by exactly `frameSize/hopSize` (confirmed live: 8x, on a device sampling at ≥48kHz where `analysisFrameSize` resolves to 4096). This distorted every timing-based decision downstream (onset confirmation windows, `ScoreFollower`'s settle/deadline timers, tempo estimation, `MetronomeScoreFollower`'s old frame-timestamp-driven scheduling before it was rearchitected to not depend on this at all — see the score-following section below) for as long as this module existed, and was invisible to the offline resync harness, which never touches this module. Now always shifts by exactly `hopSize` — no special case.

`audio/energyOnsetDetector.ts` (`EnergyOnsetDetector`) is a second, independent onset signal: frame-to-frame *relative RMS rise* on the same band-passed onset window `OnsetDetector` analyzes, rather than spectral-shape change. Meant to catch attacks flux underreacts to (a soft bowed attack, or a same-pitch re-articulation where the spectral content barely changes but the loudness still jumps). **Gated by `StartCaptureOptions.energyOnsetDetectionEnabled` (off by default) in `captureModule/index.ts` — this gate is load-bearing, not cosmetic.** The energy detector's `detect()` result independently (re)opens/extends the *same* pending-onset-awaiting-pitch-confirmation window flux does (see `pendingOnsetTimestampMs` in `processBufferedFrames`); when this shipped without that gate, a single real bow attack could produce two independent onset events (flux firing, then energy firing a few ms later, or vice versa), each capable of advancing `ScoreFollower`'s cursor via the ordinary fast path — confirmed live via `getTrace()` showing `next_note_immediate` commits 10-20ms apart, far too close to be two real bow strokes. With the gate off (default), onset firing is byte-for-byte flux-only, unchanged from before this detector existed. When both a real onset AND this detector fire within `ENERGY_FUSION_WINDOW_MS` (50ms) of each other, the confirmed onset is tagged `onsetConfidence: "high"` on `LivePitchFrame`; only one firing tags it `"low"`; with the detector off entirely, `onsetConfidence` is always `null` (no fusion was attempted, not "low confidence" by default). **Lesson for future additions in this file: "compute a signal always, gate only its downstream use" (the pattern used safely elsewhere — see `lastPitchReason` and tempo sampling below) is only safe when the signal is genuinely passive. A signal that participates in a shared trigger condition (like onset firing) is not passive, and needs its own gate at the point where it can actually change behavior, not just at whatever consumes its output further downstream.**

### Sheet music import → render pipeline (`score/`)
Two import paths normalize into the same `ScoreDocument` (`score/schema.ts`):
- `score/musicxmlImport.ts` (`importMusicXmlToScore`) parses a MusicXML string directly via `DOMParser`, walking each `<measure>`'s children in document order. It tracks `divisions`/key/time-signature/tempo as running state, handles `<backup>`/`<forward>` (multi-voice cursor repositioning), filters notes to a single `<voice>` (the app tracks one melodic line — a second voice/layer in the source is intentionally dropped), and skips grace notes (no `<duration>`, would otherwise count as a phantom quarter note).
- `score/omrImport.ts` (`importPhotoToScore`) POSTs image bytes to the Python server's `/api/parse-sheet`, then delegates the returned `xmlData` to `importMusicXmlToScore` rather than building a score from the flat `notes`/`frequencies` arrays in the response (those two arrays aren't reliably the same length — the server filters unparseable frequencies out of `frequencies` without touching `notes` — so don't zip them by index). `OmrImportResult` also carries the raw `xmlData` string alongside the parsed `score`, both for the renderer (see below) and so `App.tsx` can offer it as a MusicXML download.

**Per-measure signature changes**: `ScoreMeasure` optionally carries its own `timeSignature`/`keySignature`/`tempoBpm`, set only on the first measure and wherever a change actually occurs (not every measure). `ScoreDocument`'s top-level `timeSignature`/`keySignature`/`tempoBpm` are just the *starting* values (mirrors of `measures[0]`'s), not a piece-wide constant. This still matters for any code reading `ScoreDocument` directly (metadata display, future score-following), but no longer affects rendering — see below. `tempoBpm` is `number | null` — `null` means the source genuinely never specified a tempo, as opposed to a real authored value; `musicxmlImport.ts` used to fabricate `120` in that case, which is why this is nullable rather than defaulting.

`score/renderer/index.ts` (`renderScore(xmlData, container) → Promise<RenderedScoreHandle>` with `.unmount()`) renders directly from the raw MusicXML text via **OpenSheetMusicDisplay (OSMD)**, not from `ScoreDocument`. This replaced a hand-rolled VexFlow path that built one `StaveNote` per `ScoreNote` from the lossy `ScoreDocument` reduction — `ScoreDocument`/`musicxmlImport.ts` drops rests entirely (a rest advances the measure's beat position but is never added as a tickable), so any real piece with rests underfilled its VexFlow `Voice` relative to the time signature, producing exactly the overlapping/misaligned notation that used to show up here. `ScoreNote` also has no fields for ties, slurs, articulations, or dynamics, so the old renderer could never draw them regardless of engine. OSMD sidesteps all of this by parsing the source XML itself — `ScoreDocument` remains the internal model for metadata display and future score-following/cursor work, but is no longer in the rendering path at all. `renderScore` is async now (`osmd.load()` returns a `Promise`); callers must guard against the effect re-running before `load()` resolves.

**Beaming**: `score/renderer/beamGrouping.ts` (`applyAutomaticBeaming`) computes beam groups itself from each measure's actual time signature and writes `<beam>` elements directly into the XML before OSMD parses it, rather than relying on OSMD's `autoBeam` option. This isn't a style choice — direct testing (hand-built fixtures rendered through the real pipeline) found OSMD's own default automatic beam grouping **fails outright on a repeating pitch pattern** (a repeating 3-note phrase in 12/8 rendered completely unbeamed; an otherwise-identical varied-pitch phrase beamed correctly), reproducing regardless of key signature, `divisions` scale, or MusicXML version/DOCTYPE. "Send in the Clowns"' opening motif is exactly a repeating 3-note phrase, which is why it reliably triggered this — **don't re-attempt an `autoBeam`-only fix**, it's been ruled out against real data, not just theorized. `applyAutomaticBeaming` handles compound vs. simple meters, mid-piece meter changes (recomputed fresh per measure), multi-level beams with standard hook placement for 16th/32nd runs, and stops groups at rests/non-beamable notes/voice changes/measure boundaries; it does not account for tuplet `<time-modification>` ratios or grace notes (both pre-existing, intentional scope boundaries). Stem direction is *not* hand-computed — `renderScore` sets `setWantedStemDirectionByXml: false`, and OSMD/VexFlow's automatic stem computation is beam-aware, so it enforces one consistent direction per group on its own once `<beam>` data correctly groups the notes. `applyAutomaticBeaming` is invoked based on whether the source XML actually contains any `<beam>` elements at all (`hasBeamData()` in `score/renderer/index.ts`), not on where the score came from — it used to run only for OMR/photo-sourced scores (gated on `sourceType === "photo"`), which silently meant a directly-uploaded MusicXML file lacking its own beam data (common — plenty of exporters omit it) fell back to OSMD's confirmed-broken `autoBeam` too. A file that already carries valid beam data of its own is left untouched regardless of source.

**Time signature auto-correction** (`autoCorrectTimeSignatures`, off by default — a dev-toggle checkbox in the sheet-music-import card in `App.tsx`) exists because HOMR frequently fails to detect a real mid-piece meter change and just carries the previous `<time>` forward — confirmed live on "Send in the Clowns" (alternates 12/8/9/8/6/8/4/4 throughout), which logged dozens of beat-count mismatch warnings. Getting this right took three separate, confirmed-live bugs to work through, in order. First, the mismatch warning itself (`musicxmlImport.ts`) originally compared a measure's quarter-note total directly against the time signature's bare numerator without converting for beat-type, so every correctly-parsed 12/8 measure falsely warned ("parsed 6 beats but expects 12" — 6 quarter notes *is* 12 eighth notes); fixed by converting both sides to quarter-note units first. Second, `score/timeSignatureInference.ts`'s `inferTimeSignature()` (shared by `musicxmlImport.ts`, correcting the `ScoreDocument` model, and `score/renderer/timeSignatureCorrection.ts`, correcting the raw XML fed to OSMD — kept in sync deliberately, same rationale as the pitch-string-format rule above) infers a replacement `beats/beatType` from a measure's actual duration whenever it doesn't fit the currently active signature; inherently ambiguous (3 quarter notes fits 3/4 and 6/8 identically), so it tries the currently-active beat-type first to favor staying in the same meter family rather than defaulting to a simple-meter guess — **live-observed to still occasionally land on a nonsensical denominator** (a `47/32` correction was seen on one badly-OMR'd bar). Root cause identified: not a bug in the inference itself, but garbage-in-garbage-out — HOMR misread one of that bar's sixteenth notes as a thirty-second note, so the bar's *actual parsed duration* is genuinely 5.875 quarter notes (not the true 6), and `inferTimeSignature()` correctly finds the exact (but musically meaningless) signature that fits that wrong duration. A duration-only heuristic structurally cannot recover the true meter here, since it has no ground truth beyond durations HOMR already got wrong — fixing this needs a *note-level* correction (the misread note's own duration), which is exactly what `score/correctionUI/index.ts`'s stubbed `applyCorrection` (patches duration by note id) is for once it's wired to a real UI. **Deliberately deferred, not fixed** — revisit alongside that feature rather than special-casing it in the time-signature heuristic. Third — and the least obvious — **MusicXML time signatures are sticky/carry-forward, so the first version of this correction wrote the corrected signature into the anomalous bar but never reverted it**, meaning every later bar with no declaration of its own silently kept the correction instead of the real meter (confirmed live: notation stayed in the wrong meter for the rest of the piece after the first corrected bar). Fixed by tracking two states per measure in both files — *genuine* (only ever updated by a real `<attributes><time>` in the source; what mismatches are measured against) versus *effective* (what a sticky reader currently sees, including whatever corrections have been applied so far) — so a bar whose own duration fits genuine again, but whose effective state still disagrees, gets an explicit reverting `<time>` written back rather than silently inheriting the earlier correction forever.

**Title/composer detection**: `musicxmlImport.ts`'s `resolveTitle`/`resolveComposer` rank every `<credit>` element on the page (not just `<work-title>`) — excluding parenthetical text, arranger/rights-org boilerplate, anything matching a part name or an `<identification><creator>` name, and very short fragments — then pick the largest-font-size survivor (`credit-type="title"` wins outright if present). This exists because HOMR's own OCR/text-region detection is unreliable at the source, confirmed against 3 real test scans: it has picked a part label ("Violin 1", OCR-garbled to "ionlin1"), a truncated fragment of the real title ("STRINGS" → "Trings"), and a small rights-org credit ("(ASCAP)") instead of the actual printed title. **This heuristic is a best-effort mitigation, not a fix for HOMR's OCR accuracy** — it can only rank/filter candidates HOMR actually produced, so a case where HOMR never captured the correct text anywhere in its output (the "Trings" case) can't be recovered this way. A more robust fix (sending the source photo to a vision-capable model for a dedicated title read) was deferred — worth revisiting if this keeps coming up. The resolved title/composer are also injected into the XML given to OSMD (`renderScore`'s `titleOverride`/`composerOverride` → `applyMetadataOverrides` in `score/renderer/index.ts`, via OSMD's `onXMLRead` hook) so the rendered score and the metadata card never disagree.

Pitch strings are formatted consistently as `<Step><#|b|><Octave>` (e.g. `C#4`, `Bb3` — single accidental only, no double sharps/flats) across two independent implementations that need to stay in sync if this convention changes: `server/main.py`'s `_note_name_to_frequency` and `score/musicxmlImport.ts`'s `pitchToNoteName`. (`score/renderer/index.ts` no longer has its own pitch-parsing regex — OSMD reads `<pitch>` elements straight from the XML.)

`score/correctionUI/index.ts` has one real function (`applyCorrection`, patches pitch/duration on notes by id) but no actual UI — it's a data-layer stub, not wired to any component.

### Score-following + practice review (`practice/`)
`practice/cursor.ts` (`ScoreFollower`) and `practice/reviewSummary.ts` (`summarizePracticeSession`) are implemented and wired into `App.tsx`: `ScoreFollower` consumes live capture frames plus the `ScoreCursor` from `score/renderer` to advance through the score note-by-note, tracks median cents-off per note, and produces a per-note history that `reviewSummary.ts` reduces into a post-session summary (out-of-tune note count, average cents error) shown in `App.tsx`. This has been through several redesigns; what follows is the current architecture and the load-bearing reasons behind it, so future changes don't quietly re-break what live testing already found.

**Two independent note-change triggers**, both funneling into the same resolution order (immediate-next-note fast path → settle-gated offset-0 re-attack no-op → multi-note sequence resync): `audio/onsetDetector.ts`'s `frame.onsetDetected` (an ordinary bowed attack), and `practice/implicitOnsetWatcher.ts`'s `ImplicitOnsetWatcher` (a sustained pitch drift away from `current`'s expected frequency, held for `implicitOnsetMinStableMs` — 200ms — with no real onset ever firing). The second exists because spectral-flux onset detection has no attack transient to catch on a legato/slurred bow change and would otherwise silently strand the cursor on the departing note forever. When neither the fast path nor the offset-0 re-attack resolves a pending transition, `resolveAdvancePendingTransition` accumulates the settled pitch into a persistent multi-note buffer (`outOfSyncSequence`) and searches the score for where that sequence matches, committing once uniquely resolved (or once the buffer hits `resyncMaxSequenceLength`, using the closest remaining candidate) — committing off a single ambiguous note (e.g. a repeated pitch appearing more than once nearby) lands on a stale, already-passed position while the player has already moved on, so a short sequence is used as a stronger fingerprint, and the commit offset lands on the *last* note of the matched sequence (not one past it) so the player's next note is immediately back in sync rather than still catching up.

**Fuzzy (edit-distance-tolerant) sequence resync matching** (`fuzzySequenceMatchingEnabled`, off by default) loosens `findSequenceMatches()`'s exact-contiguous-only requirement, which otherwise means a single missed/garbage reading anywhere in the resync candidate window breaks that whole candidate — the diagnosed reason resync used to resolve rarely on real playing. Two independent tolerance modes, each producing a `SequenceMatch.editDistance` used for ranking (lower always wins; see `pickClosestSequenceMatch`):
- **Deletion-tolerant** (`matchSequenceWithSkips`): the score has notes the player's onset detection never caught — tolerates up to `fuzzySequenceMaxSkips` (default `1`) *consecutive* missed notes, greedily matching each observed reading against the earliest still-available score position. Never discards anything the player actually played, so it's the safer half — **confirmed live at the default (1 skip)**: correctly bridges a single missed note. Bumping `fuzzySequenceMaxSkips` higher (2+) does extend this to bigger gaps, but was live-confirmed to also raise a real risk: on a passage with a repeated-pitch pattern, a farther *coincidental* position can end up needing *fewer* skips to explain the last few readings than the true, closer position does, and since skip count is the primary ranking signal, the wrong-but-cheaper match wins — this manifested live as the cursor occasionally jumping *past* the player, not just catching up (see `fuzzySequenceMaxSkips`'s config doc comment). No further mitigation has been attempted yet; treat any value above the default as a deliberate, closely-watched experiment, not a safe default bump.
- **Insertion-tolerant** (`sequenceMatchesWithInsertion`, gated by the *separate* `fuzzyInsertionMatchingEnabled`, off by default even when the deletion mode is on): the observed sequence has an extra reading that isn't a real score note (noise, a duplicate re-articulation) — excludes it from matching entirely. **Confirmed live to be the riskier of the two and left off**: a live incident (3-reading buffer, middle reading was genuine noise) resolved by discarding a *real* reading instead — one nearly identical in pitch to another in the buffer — landing a resync short of the player's actual position. Ranked strictly worse than any deletion-tolerant match (a fixed `INSERTION_EDIT_DISTANCE` sentinel, not just "+1") specifically because it discards real evidence rather than merely tolerating a gap in the score.

**`implicitOnsetStabilityToleranceSemitones` (`1.5`) is tuned around a real live tradeoff — don't casually re-tighten it.** Originally `0.6` (tight enough to reliably catch even half-step legato transitions), but live testing found *heavy* violin vibrato on a held note was itself misread as an advance to the next note — vibrato depth and "smallest real legato transition" genuinely overlap in magnitude and aren't cleanly separable by a semitone threshold alone. Raised to `1.5` (cluster tolerance to `2.2` to match — the running-centroid/EMA internal-consistency check that lets vibrato on the *arrival* note not break the drift-tracking run before it can trigger). This deliberately means half-step legato transitions are no longer reliably caught via this path; they fall back to `OnsetDetector` or eventual sequence resync instead. This is also why the `expectedFrequencyHz` pitch-detection narrowing hint mentioned above stays unwired: it hard-rejects a reading more than a few semitones from the hint, so if the score-position hypothesis feeding it were ever wrong, it would suppress the very evidence needed to detect and correct that — turning it on needs its own safeguard (e.g. suppressing/widening the hint whenever the follower isn't confident it's in sync), not just a wire-up.

**Adaptive stability window** (`adaptiveStabilityWindowEnabled`, off by default) scales `ImplicitOnsetWatcher`'s `minStableMs` per-note by an empirical tempo estimate instead of always using the fixed `implicitOnsetMinStableMs` (200ms). Rationale: at a fast tempo a note can genuinely last less than 200ms, meaning the implicit trigger could never fire for it in time no matter how real the legato transition is. `ScoreFollower.recordTempoSample()` records `(actual elapsed ms / the outgoing note's notated duration)` on every committed transition (always on, cheap, harmless when unused — same "compute freely, gate the use" pattern as `lastPitchReason` below, and safe here specifically *because* a tempo sample is passive bookkeeping, unlike the energy-detector case above), keeps a short rolling median (`tempoEstimateSampleCount`, default 4; notes shorter than `tempoEstimateMinQuarterNotes` are never sampled — their observed timing is dominated by settle/onset-detection latency relative to their own short length). `computeAdaptiveMinStableMs()` then multiplies the current note's notated duration by that estimate and by `adaptiveStabilityWindowFraction` (0.75), floored at `adaptiveStabilityWindowFloorMs` (150ms — must stay above one full violin vibrato cycle, same reasoning as `implicitOnsetStabilityToleranceSemitones` above). Needs `CursorNoteInfo.durationQuarterNotes` (`score/renderer/scoreCursor.ts`, read off OSMD's `Note.Length.RealValue * 4` — quarter-note units, matching `ScoreNote.durationBeats`'s convention in `score/schema.ts` even though it's computed differently). Live-tested and left on with mixed but non-negative results — the mechanism only affects the implicit (no-bow-attack) trigger, which is a minority of transitions in normal bowed playing, so its live impact is inherently narrow; don't expect this alone to be felt strongly.

**Reverted redesign — do not re-attempt continuous best-fit alignment as a quick fix without accounting for why it failed.** A more ambitious redesign replaced the discrete state machine above with continuous alignment: a sliding window of recently-played pitches, re-searched via a gap-tolerant backward walk against the score on every note event (tolerating silently-missed notes), requiring 2 corroborating matches for any jump beyond the immediate neighbor. It passed the full offline test suite (synthetic, noiseless test tones) but live testing found it **got stuck and didn't move forward, and sometimes jumped to a random note**. Un-confirmed but likely cause: requiring multiple clean corroborating readings *multiplies* dependency on already-unreliable pitch/onset signal reliability rather than reducing it, and gap-tolerant matching over a wide search window increases false-positive risk on real pieces' repeated pitches/patterns (scales, arpeggios) in a way the hand-built, deliberately-distinct-pitch offline tests never exercised. Reverted back to the discrete state machine described above.

**Tied and slurred-same-pitch notes are skipped as landing positions.** `score/renderer/scoreCursor.ts`'s `isTickable()` treats a note as non-tickable (same as a rest) if it's the continuation of a `<tie>`, or of a `<slur>` connecting the *same* pitch (some sources — hand-authored or OMR-generated MusicXML — mark a same-pitch connector this way instead of the technically-correct `<tie>`; musically identical, so treated the same). Without this, `ScoreFollower` waits forever: a tied/same-pitch-slurred note produces no new onset (no re-articulation) and no pitch change (so `ImplicitOnsetWatcher` can't fire either). Deliberately narrow — a slur connecting *different* pitches is an ordinary legato phrase mark and those notes still need separate tracking, since the pitch genuinely changes (that's what `ImplicitOnsetWatcher` is for). The slur check compares against the slur's own `StartNote`, so it's correct for a simple two-note slur but won't catch a same-pitch repeat buried inside a longer, multi-pitch slur.

**End-of-piece completion needs both a return-value fix and a physical-cursor fix — if the cursor visually drifts to the final barline instead of disappearing when a piece ends, check both.** `ScoreCursor.advanceBy()`/`retreatBy()`/`advanceToNextNote()`/`retreatToPreviousNote()` must return `null` when there's truly nothing left (not clamp to the old note) for `ScoreFollowerState.status` to ever reach `"completed"` — but that alone is insufficient, because the internal search that discovers "nothing left" has already moved the *real* OSMD cursor object forward via genuine `next()` calls while searching for a note that doesn't exist, so drawing at that point (`osmdCursor.update()`) still redraws the stale, drifted position regardless of what the function returns. The actual fix calls `osmdCursor.hide()` instead of `update()` specifically on that "nothing left" path.

**Energy onset fusion consumption**: `ScoreFollower.extraSettleMsFor()`, gated by `energyOnsetFusionEnabled` (off by default, independent of `energyOnsetDetectionEnabled` in `captureModule` — both need to be on for this to have any effect), gives a pending transition extra deadline/settle patience (`lowConfidenceOnsetExtraSettleMs`, 100ms) when the onset that opened/most-recently-extended it was fusion-`"low"` confidence (`LivePitchFrame.onsetConfidence`, see the live tuner pipeline section above). `PendingTransition.onsetConfidence` is re-derived from whichever onset most recently extended the transition (not fixed at the original onset), so a later higher-confidence onset correctly shrinks the window back down rather than leaving it stuck at an earlier extension. `null` (not "low") for `triggerSource: "implicit"` — that trigger already has its own confidence mechanism (a sustained hold over `minStableMs`) and fusion was never attempted for it.

**Same-pitch repeated notes without their own samples inherit the previous note's verdict.** `finalizeCurrentNote()`: a note that collects zero pitch samples (would otherwise report `"not_played"`) but is an exact-frequency repeat of the immediately preceding, already-measured note copies that note's `verdict`/`averageCentsOff` instead, flagging `NoteAccuracyRecord.inferredFromRepeat: true` so it stays distinguishable from a real measurement. This exists because repeated-note passages (e.g. "Twinkle Twinkle"'s "D D") routinely left the *second* note of a pair with no settled window distinct enough from the first to collect any samples of its own — live-observed on one playthrough as 12 of 42 notes (29%) silently reporting `"not_played"` despite `getTrace()` confirming every one was actually tracked through via a real onset. Deliberately narrow: requires *exact* frequency equality (not a semitone-tolerance comparison — both values come from the same `CursorNoteInfo.primaryFrequencyHz` computation for a written pitch, so a real repeat is exactly equal, never approximately), and never chains from a neighbor that's itself `"not_played"` (no inference from unmeasured to unmeasured). Does **not** help when *both* notes in a pair come up empty — that still needs the root cause (why the settled window misses samples at all on some notes) looked at directly, not just papered over.

**Plausibility gate (shared with `MetronomeScoreFollower`)**: `cursor.ts`'s exported `isPlausibleReading()` decides whether a detected pitch reading is trusted as real evidence toward a note's score at all, applied identically by both followers right before a sample would be pushed into `centsOffSamples`. Three tiers: (1) a hard, confidence-independent ceiling — `plausibilityAbsoluteCentsLimit` (1000 cents, most of an octave) — rejects a reading no matter how confident the detector was; (2) at or above `plausibilityHighConfidenceThreshold` (0.8) and under that ceiling, the reading is trusted regardless of how far off it is (genuine severe mistuning is real evidence, not something to discard); (3) below that confidence, it additionally needs to be within `plausibilityLowConfidenceCentsLimit` (250 cents) of the expected pitch. Exists because low-confidence readings 1500-2000 cents off (silence/noise artifacts that still cleared the base pitch detector's own confidence floor) were producing false `"out_of_tune"` verdicts on notes nobody played — tier 3 alone caught that, but tier 1 was added after confirming live that a clean, *confidently*-detected tone (the metronome's own click bleeding into the mic — see the metronome section below) could still slip through tier 2 unbounded.

**Diagnostics**: `ScoreFollowerState.lastPitchReason` mirrors the most recent live frame's `LivePitchFrame.reason` (see the live tuner pipeline section above) — purely diagnostic, drives no decision, but distinguishes "the player genuinely stopped" from "the detector is rejecting real signal" when tracking seems stuck. `ScoreFollower.getTrace()` returns a ring buffer of tracking decisions — reason, offset, `triggerSource`, `editDistance` (which fuzzy-matching tier resolved it, if any — `null` when the fast path or a direct pitch check resolved it instead), `sequenceLength` (how many buffered readings the match used), and `onsetConfidence` (the fusion confidence of the onset behind the decision, when applicable). `src/App.tsx` exposes the live instance at `window.__scoreFollower` for pulling this from the browser console during live testing — static reasoning alone has repeatedly been insufficient to diagnose behavior in this feature that only shows up live; use it before another redesign attempt rather than guessing again. In this session, `getTrace()` was what distinguished a genuine resync/ambiguity problem from a completely different bug (two onset events firing per bow attack, visible only as suspiciously-close-together `next_note_immediate` timestamps with zero resync activity anywhere in the log) — don't assume every "cursor moved wrong" report is a resync/matching issue without checking the trace shape first.

**Offline verification**: no Jest/Vitest in this repo. `practice/__tests__/resync-harness.ts` (run via `npm run followerTest`, 34 scenarios as of this writing) exercises `ScoreFollower` against a mock `ScoreCursor` (plain array, pure index arithmetic) with hand-built synthetic frame sequences. It cannot catch three categories of bug that have bitten this feature in practice: anything involving the *real* OSMD cursor object (the tie/slur/completion fixes above, or `peekWindow()`/`peekNextNote()` traffic desyncing the visual cursor from logical state — OSMD ships only a minified bundle here, so its `next()`/`previous()`/`update()` internals have never been directly verified, only inferred from the `.d.ts` contract); anything involving real (noisy, imperfect) pitch/onset signal quality, since the harness's synthetic tones are perfectly clean; and — confirmed the hard way by the energy-onset-detector gating bug above — anything in `audio/captureModule/index.ts` itself, since this harness feeds `ScoreFollower` pre-built `LivePitchFrame` objects directly and never touches the capture module at all. A change that's entirely correct at the `ScoreFollower` level can still ship a real behavior change in the audio layer underneath it that this harness cannot see, green run or not. All three categories need a live re-test.

**Live validation status (this session)**: on a simple, single-voice, moderate-tempo piece ("Twinkle Twinkle Little Star" difficulty — mostly separately-bowed notes, minimal legato, no fast runs), with `fuzzySequenceMatchingEnabled` on at the default `fuzzySequenceMaxSkips` (1) and the energy-onset-detector gating bug fixed: cursor tracking required zero resync activity for the whole piece (every transition resolved via the ordinary fast path), and post-fix intonation reporting produced a coherent, specific pattern (open strings and easy fingered notes measured accurately; notes requiring less-anchored finger placement measured consistently flat by a repeatable amount) rather than noisy scatter — evidence the underlying cents measurement is trustworthy for what it does measure, on a piece this simple. Not yet re-validated live on anything faster, multi-voice, or with real legato phrasing; `fuzzySequenceMaxSkips` above the default and `fuzzyInsertionMatchingEnabled` remain live-risky per above and are off/at-default pending further evidence.

### Metronome-driven tracking (`practice/metronome.ts` + `practice/metronomeFollower.ts`)
A second, independent tracking mode, added alongside (not replacing) the pitch/onset-driven `ScoreFollower` above, per this session's finding that pitch-based following isn't reliable live. This has been through a full redesign since it first shipped; what follows is the current architecture.

**Single clock, not two.** `practice/metronome.ts`'s `createBeatClock()` is the sole source of truth for timing — cursor advancement and the audible click both originate from the *same* scheduled callback, not two independently-clocked systems. An earlier version scheduled the click against its own `AudioContext` while `MetronomeScoreFollower` scheduled cursor advancement against microphone-input frame timestamps from a *different* `AudioContext` — two clocks that could never be perfectly aligned no matter how well-tuned, confirmed live as a small but consistently perceptible lag between the audible beat and the cursor actually moving. Now `BeatClockOptions.onTick` (fired via a per-tick `setTimeout` landing at the real-time instant each tick is scheduled for, using the standard lookahead-scheduler pattern so the underlying audio stays glitch-free) is the only thing that calls `MetronomeScoreFollower.advanceOnTick()` — the audible click and the visible cursor are reactions to the literal same event.

**Tick resolution vs. click resolution are different.** The clock always ticks internally at sixteenth-note resolution (`FINE_SUBDIVISIONS_PER_QUARTER`, 4) regardless of what's audible, so `advanceOnTick(quarterNotesElapsed)` can resolve any notated duration down to a sixteenth note accurately (`MetronomeScoreFollower` accumulates `quarterNotesElapsed` against the current note's own duration in a `while` loop, so a note shorter than one tick can't strand the cursor by more than one tick). The audible click's *density* is a separate, configurable choice — see click subdivision below — but never affects scheduling precision.

**Click subdivision toggle** (`ClickSubdivision`: `"auto" | "quarter" | "dottedQuarter" | "eighth"`, `App.tsx`'s `clickSubdivision` state, default `"auto"`). `"auto"` resolves to a plain quarter for simple meters but a *dotted* quarter for compound meters (`resolveClickSubdivision()`: denominator 8, numerator a multiple of 3 and ≥6 — 6/8, 9/8, 12/8, ...), since that's the actual felt beat there. This exists because a fixed quarter-note click is musically wrong in a compound meter — confirmed live on a 12/8 piece reported as "didn't work at all" (not just miscounted): 6 plain-quarter clicks per bar instead of 4 dotted-quarter clicks is a completely different, unrecognizable pulse, even though the underlying bar-duration math (`quarterNotesPerMeasure()`) was already correct. `clicksPerMeasure` is always derived from the *actual* bar duration divided by the chosen subdivision's tick interval, so the count-in bar's total duration matches the real measure exactly regardless of which subdivision is audible.

**Mid-piece meter changes** (`computeTimeSignatureSegments()`): the beat clock originally computed its click's beat-grouping/downbeat pattern *once*, at session start, from the score's *opening* time signature only (`ScoreDocument.timeSignature`, which per the per-measure-signature-changes note above is explicitly just `measures[0]`'s value) — a real meter change mid-piece just kept getting clicked as though the piece never left its first measure's meter, even though `MetronomeScoreFollower.advanceOnTick()` itself was already meter-agnostic (walks real per-note durations off the OSMD cursor, unaffected by which measure/meter a note sits in). `computeTimeSignatureSegments()` derives an ordered `{startQuarterNote, timeSignature}` list from `ScoreDocument.measures` (a new segment wherever `measure.timeSignature` is actually set — a genuine or auto-corrected change; see the time-signature auto-correction note above). `createBeatClock()` now precomputes click/downbeat parameters (resolved subdivision, `clicksPerMeasure`) *per segment* instead of once globally, and on every tick looks up the active segment from elapsed real-piece time, resetting click/downbeat counting relative to that segment's own start (always exactly a measure boundary — a MusicXML meter change can't land mid-measure). The count-in still always uses the piece's opening meter regardless of what comes later. Scope boundary: segment timing follows each measure's *declared* signature (via `quarterNotesPerMeasure()`), not an independently-recomputed actual-duration walk — a bar whose real duration doesn't match its declared signature drifts the click too, unless `autoCorrectTimeSignatures` is on (which fixes the notation and the click for the same reason, since both read from the same corrected `ScoreDocument`/XML).

**`quarterNotesPerMeasure()` rounding bug (fixed) — latent since before this session, only surfaced once a real 9/8 segment existed.** It was rounding its result to the nearest whole quarter note (`Math.round(...)`), silently wrong for any meter whose beat-type produces a genuinely fractional quarter-note count — an odd numerator over an eighth-note beat (9/8 = 4.5 quarter notes; `Math.round(4.5)` rounds *up* to 5). Confirmed live as a spurious extra click at the end of a 9/8 measure, delaying the next measure's downbeat by a full beat. Every meter this app had been exercised against before (6/8, 12/8) has an even numerator, which happens to round to an exact integer, which is exactly why this never surfaced until mid-piece correction produced a genuine odd-numerator segment. Fixed by not rounding at all — safe because every consumer either multiplies the value by the clock's own sixteenth-note tick resolution (which any eighth-note-based fraction divides evenly into) or rounds the *final* click count itself where an integer is actually required (`createBeatClock`'s own `clicksPerMeasure`).

**AudioContext robustness**: `createBeatClock`'s scheduler resumes a suspended `AudioContext` automatically on every poll (a suspended context's `currentTime` freezes, which otherwise silently and permanently stopped the click — confirmed live as "randomly stops making noise" with no error), and resyncs forward instead of firing a burst of "overdue" ticks when it finds itself more than `MAX_CATCHUP_GAP_SECONDS` (1.5s) behind the audio clock (Web Audio clamps a past `oscillator.start()` time to "now," so a catch-up burst meant several oscillators at slightly different pitches all starting at once — confirmed live as a dissonant/"broken bass noise" sound). A large gap now behaves like practice paused, not like noise.

**The click bleeds into the mic — masked, not just filtered.** The click plays through speakers, which the microphone can pick up as a clean, confidently-detected tone (indistinguishable from a real note by pitch/confidence alone, and confirmed live to slip past the plausibility gate below even after that gate existed). `BeatClockOptions.onClick` fires — via the same per-tick real-time callback as `onTick`, so it's exact, not approximated — at the instant a click actually plays; `MetronomeScoreFollower.notifyClickPlayed()` masks incoming pitch samples (and bow-attack detection, see below) for `clickMaskMs` (250ms, covers the click's own ~70ms plus room reverb/mic latency headroom) afterward.

**Plausibility gate**: see `isPlausibleReading()`'s writeup in the score-following section above (shared with `ScoreFollower`) — `plausibilityAbsoluteCentsLimit` (1000 cents) is the confidence-independent backstop for whatever gets past click-masking or any other source of a clean-but-wrong reading.

**Rests are not silently skipped.** `ScoreCursor`'s forward walk has always skipped rest positions when finding the next tickable note (fine for the pitch-driven `ScoreFollower` — a rest there just means no onset fires for a while, which its onset/implicit-drift machinery already tolerates) — but a strictly clock-driven follower needs that time accounted for, or the cursor races ahead of real time for the rest of the piece once a rest is skipped. `CursorNoteInfo.precedingRestQuarterNotes` (accumulated during the *forward* walk only — `landOnNextNonRestNote`, `peekNextNote`, `peekAhead`; the backward walk always reports 0, since nothing consuming it needs backward rest timing and the correct backward value is semantically different, not just unused) carries the preceding rest's duration, and `MetronomeScoreFollower.effectiveDurationQuarterNotes()` folds it into how long the *preceding* note stays current (a rest has no note of its own to display, so its time extends the note before it rather than getting its own landing position).

**Tied notes are not silently truncated either — same bug shape as rests, same fix shape.** `isTickable()` already treats a tie/same-pitch-slur continuation as non-landable (one continuous sound, no re-attack — see the score-following section above), but nothing accounted for the *continuation's own duration* until this session: it was silently dropped from the schedule exactly like a skipped rest was, just via a different code path. Confirmed live: a dotted-half tied to a dotted-quarter (9 eighth notes total) was only held for 6 — exactly the dotted half's own length, with the tied dotted quarter's duration lost outright. `scoreCursor.ts`'s `accumulateTiedContinuationQuarterNotes()` (called from all five `CursorNoteInfo`-construction sites, including the backward ones — unlike the rest case, tie-extra-duration is a property of "what comes after this note" and is computed identically regardless of which direction the caller walked to arrive there) walks forward temporarily from a just-landed note, accumulating any immediately-following tie/slur continuations' durations (handling a longer chain, not just one link) into that note's own `durationQuarterNotes`, and always rewinds the cursor back to the landing position before returning.

**Bow attack detection toggle** (`bowAttackDetectionEnabled`, off by default — `App.tsx`'s `bowAttackDetectionEnabled` state). Off: the cursor advances strictly on the beat clock's schedule, full stop — this is what guarantees zero disagreement between the audible click and the visible cursor. On: reintroduces a bounded version of an earlier (fully reverted) design where a real bow attack (`LivePitchFrame.onsetDetected`) whose pitch is clearly *closer* to the upcoming note than the current one (a comparative check, not just an absolute tolerance — two adjacent notes a semitone or two apart, ordinary stepwise motion, are both easily within any reasonable absolute cents tolerance of a reading that's actually still the outgoing note) can shift the cutover early or late, within `bowAttackToleranceQuarterNotes` (0.5) of the clock's own boundary. This directly targets a real problem (a late player's tail bleeding into the new note's score, or an early player's head bleeding into the old one) at the explicit cost of reintroducing bounded clock/attack disagreement — an opt-in trade, not a silent default. `checkBowAttack()` and the tick-driven `isDueToAdvance()` share one commit path (`commitAdvance()`) so both stay consistent about what "starting a new note" resets; masked (via `notifyClickPlayed()`) exactly like ordinary sampling, so a click can't fake a bow attack either.

Reuses `ScoreFollower`'s `centsOff`/`median`/`createEmptyRecord`/`isPlausibleReading`/`semitoneDistance` helpers (exported from `practice/cursor.ts`) and produces the exact same `ScoreFollowerState` shape, so `src/App.tsx`'s practice UI works against either follower unmodified — `App.tsx`'s `trackingMode` state (`"listening" | "metronome"`) picks which class `handleStartPracticing()` instantiates. Because this mode never resyncs (even with bow attack detection on — that's a bounded local correction, not a resync mechanism), it carries none of `ScoreFollower`'s resync-specific state (`getTrace()`, fuzzy matching, tempo estimation).

**Live validation status (mid-piece meter changes, this session)**: the segment-lookup mechanism and the `quarterNotesPerMeasure()` fix were both diagnosed and fixed against a real live report on "Send in the Clowns" (a corrected 9/8 measure produced an audible extra click before the next measure's downbeat) — not yet re-confirmed live after the fix. Re-verify that transition (and any other odd-numerator segment in the piece) actually lands its downbeat on time before trusting this further.

**Live validation status**: the beat-clock unification, plausibility tiers, rest/tie duration fixes, and subdivision toggle were all implemented and offline-verified (synthetic scenarios against a mocked `ScoreCursor`, same technique as `resync-harness.ts` but ad hoc — this mode still has **no permanent offline harness**, since `resync-harness.ts` only exercises `ScoreFollower`) in the same session that diagnosed each live bug, but the tied-note fix specifically has **not** been live-verified — it lives inside `scoreCursor.ts`'s real OSMD `Cursor`/`Note` interaction, which can't be mocked the way the follower logic can without a browser. Re-verify the 9-eighth-notes tie case live before trusting it further. The click-mask bump (150ms → 250ms) and the absolute cents cap were both responses to "still triggering" reports without full diagnostic confirmation of root cause on the mask side specifically — worth confirming live that the click is now fully suppressed, not just capped after the fact by the 1000-cent ceiling.

### UI
`src/App.tsx` is the only React component in the app (no `components/`/`hooks/` directories exist) — plain `useState`/`useRef`, inline `CSSProperties` style objects in a `styles` const, dark card-based visual theme. It has two independent sections: the live tuner (drives `captureModule`) and the sheet-music import card (drives `omrImport` → `renderer`) — they don't share state.

**Tracking mode selector**: visible only while `practiceMode === "off"`, a radio pair sets `trackingMode` (`"listening"` | `"metronome"`) — see the metronome-driven tracking section above. Selecting `"metronome"` reveals: a BPM number input (`metronomeBpm`, defaulting to the imported score's `tempoBpm` when present, else 90; the field deliberately does *not* clamp on every keystroke — see its inline comment for why that broke typing multi-digit values — clamping happens on blur and again defensively at follower-construction time); a "click throughout practice" checkbox (`metronomeClickThroughoutEnabled`, off by default — the one-bar count-in always clicks regardless); a click subdivision `<select>` (`clickSubdivision`); and a bow attack detection checkbox (`bowAttackDetectionEnabled`). All hidden/inert in listening mode.

**Count-in flow**: `practiceMode` has a third state, `"counting_in"` (metronome mode only — listening mode goes straight from `"off"` to `"active"`, no count-in). `handleStartPracticing()` creates a `BeatClock` and calls `.start()`; `beginFollowing()` (constructs and starts the actual `ScoreFollower`/`MetronomeScoreFollower`, shared by both tracking modes) is deferred until `onCountInComplete` fires, so the follower's first note begins at the exact instant the count-in bar ends. The "Practice this score" button becomes "Counting in… (cancel)" during this state (`handleCancelCountIn()`) rather than just disabling, since there's no session yet to fall back to if the user backs out mid-count-in.

**Double-session-start bug (fixed).** `handleStartPracticing()` originally had no re-entrancy guard at all — clicking "Practice this score" more than once while a session was already `counting_in`/`active` (e.g. a few impatient clicks before the button visibly swaps to "Counting in… (cancel)") created ANOTHER `BeatClock` (its own `AudioContext`, `setInterval` scheduler, eventual `MetronomeScoreFollower`) on top of the one already running, since nothing ever stopped the previous one before `beatClockRef.current` was overwritten. Confirmed live: a handful of rapid clicks produced several concurrent clocks/followers all independently advancing the SAME shared `ScoreCursor` — the visible symptoms were severe lag (browser "setTimeout handler took Nms" violations from Nx the scheduling work), the audible click glitching, and the cursor freezing/jumping (multiple independent `advanceToNextNote()` calls racing on one mutable OSMD cursor object). A first fix (checking `practiceMode !== "off"` at the top of `handleStartPracticing()`) turned out to be **insufficient on its own**: React state isn't visible in a closure until the next render commits, and several rapid clicks landing before that commit (which is exactly what happens under the jank this bug itself causes — a bad feedback loop) can all still read the stale `"off"` value. Fixed by adding `sessionStartingRef` (a plain `useRef<boolean>`, set synchronously the instant a session starts, cleared at every point a session actually returns to `"off"`) alongside the state check — a ref mutation is visible to the very next synchronous call with no render in between, unlike state. **Follow-up bug from an incomplete fix**: the ref was initially cleared at three explicit teardown sites (`handleCancelCountIn`, `handleStopPracticing`, the `renderScore` effect's cleanup) but NOT in the fourth, actually-most-common one — the `followerState`-watching effect that sets `practiceMode` back to `"off"` when a session genuinely finishes (piece completion) or the user clicks "End Practice" (both funnel through that one effect, not through `handleEndPracticing()` itself, which deliberately leaves `practiceMode` at `"active"` to show the summary first). Missing the reset there meant the guard did its job exactly once per page load — the button silently did nothing on every subsequent click after the very first practice session ended, since `practiceMode` was legitimately back to `"off"` but the ref never was. Lesson: when a guard has multiple legitimate exit paths, grep for *every* place the corresponding state actually resets, don't assume the handful of obviously-named handlers are the complete list.

**Dev-only feature toggles**, visible only while `practiceMode === "off"` and `trackingMode === "listening"` (so they can't be flipped mid-session, and don't clutter the unrelated metronome mode): checkboxes for `fuzzySequenceMatchingEnabled` (with a number input for `fuzzySequenceMaxSkips`, only shown once that's checked), `adaptiveStabilityWindowEnabled`, and `energyOnsetFusionEnabled`, each passed into `new ScoreFollower(scoreCursor, {...})` in `handleStartPracticing`/`beginFollowing`. `energyOnsetFusionEnabled` additionally gets passed as `energyOnsetDetectionEnabled` into `controller.start()` in `handleStart` (the capture-module-side gate for the energy onset detector) — **that half only takes effect on the next microphone start, not live**, since capture options are fixed at `controller.start()` time same as every other capture option; toggling the checkbox after the mic is already running requires a stop/start to actually change anything. These exist for live A/B testing each mechanism via `window.__scoreFollower.getTrace()` without editing code — remove each once its feature is fully live-validated and its config default is flipped for real.
